#### 需修正的证据

**1. 方向三，证据 2（文件上传不做内容检查）：**

文档说"文件上传不做内容检查"，不够精确。实际代码中**MIME type allow-list 已实现**（`mimeAllowed` 方法 + `allowed_mime_types` 配置项）。缺失的是**图像内容级审核**（NSFW/暴力检测）。建议改为：

> 虽然文件上传已实现 MIME type allow-list，但这仅过滤文件**类型**，不检查文件**内容**。一个 `.jpg` 文件可以是通过 MIME 校验的合法图片，也可能是 NSFW 内容——内容级审核完全缺失。

**2. 方向五，证据 4（CORS）：**

文档写"CORS 中间件对所有来源开放或单一来源"，实际代码支持**可配置的多来源 allow list**：`CORS(origins []string)` 支持多个来源，空列表时才全部开放。建议修正代码引用以反映这一细节：

> ```go
> // internal/middleware/cors.go
> func CORS(origins []string) gin.HandlerFunc {
>     allowAll := len(origins) == 0 // 空列表 ⇒ 全部开放
> ```
> 虽然有来源白名单机制但在 API 密钥/OAuth2 缺失的背景下，无法实现 per-client 粒度的 CORS 控制。

### 文档的主要遗漏

**1. 方向三未充分利用已有的审核基础设施**

现有的 `CommentStatus`（Normal/Deleted/Hidden）、`ReportStatus`（Open/Resolved/Dismissed）、`PermContentModerate` 权限 + audit log + 评论编辑构成了**一个完整的人工审核流水线**。文档描述为"完全依赖人工处理"准确，但未指出这些已有组件使 Phase 1 的集成路径远比从零开始容易——只需在 `comment.Create` 中插入一个 moderation pipeline hook，复用已有的 `CommentStatus` 和 `ReportStatus`。

**2. 方向一未讨论配额与存储 GC 的交互**

配置中已有 `storage.gc.retention: 168h`（7 天）。软删除的文件在 GC 清理前仍占物理空间，配额释放的时机策略（软删除时 vs hard delete 时）涉及用户体验和实现复杂度的权衡，文档未讨论。

**3. 方向二未讨论通知偏好与群发 fan-out 的交互**

现有 `notification_preferences`（含 DND 时段、通知类型启用/禁用）和 notification collapse（5min 窗口）与群发 fan-out 有复杂的交互：群消息可能产生大量被 rate-limit 压制的通知。

**4. 缺少一个方向：多租户/命名空间隔离**

对于 "data owned by accounts" 平台，多组织/多团队场景（workspace/namespace）是自然的演进方向——所有数据共享同一表（`owner_uid` 列），没有隔离层。这个方向未被任何文档独立论证过。
