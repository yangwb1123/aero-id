## 总体反馈

报告的质量极高——从代码层（`UpdateContent` 直接执行 UPDATE）溯源到架构层（数据丢失链），再到产品层（UX 信任），论证链完整。每个方向都注意到了与现有基础设施的复用关系（如 outbox、通知、GC），这是深入理解代码后才能做到的。

---

## 几个值得深挖的点

### 方向一（乐观锁）—— `expected_version` 可选的设计

报告里指出"缺失时跳过检查"实现向后兼容，这个策略很好。不过有个小补充：**对于多设备用户，编辑框打开后如果被其他设备编辑过，提交时应该明确提示"内容已被修改"**。如果只用可选的 `expected_version`，旧版客户端会一直静默覆盖。建议引入一个过渡期：

1. 新 API 要求 `expected_version` 必填
2. 旧版客户端通过 `If-Match` header 或请求体中的 `expected_version` 传递
3. 过渡期内（比如 2 周），缺失 `expected_version` 的请求 **打 log warning + 记录指标** 但不拦截
4. 之后切换为必填

### 方向五（异步文件处理）—— MIME 魔数检查的优先级

报告在排序中把文件处理列为 P2，但附录里说"MIME 魔数检查做最低安全防护（较低成本）"非常关键。实际上 **MIME 验证完全可以单独拆出，作为一个独立的小步先行切入**，不依赖整个异步管道。这个改动量很小（几行 buf 读取），安全收益却很高。

### 方向四（数据可移植性）—— 审核日志的脱敏

报告里建议`审核日志保留（保留审计链，但脱敏 actor_uid → hash）`——这里有个细节：如果 hash 是确定性哈希（如 SHA256(uid + salt)），那么同一 uid 的所有日志在哈希后仍然可被关联追踪，与脱敏的目的矛盾。建议用**密钥加盐 + 只保留不可逆哈希**，或在擦除后完全删除日志行（如果合规允许）。

### 方向二（群聊）—— 与现有 1:1 的融合

`conversation_id` 可为 NULL 的兼容方案很务实。建议再考虑一个**视图层融合**的方案：在 `conversations` 表中为每个 1:1 对自动创建一个 `type=1:1` 的 conversation（惰性创建），这样所有消息在 UI 层面统一通过 `conversation_id` 寻址，而不需要 UNION。代价是需要一个后台迁移，但长期收益更高。

---

## 一个额外的小建议

报告中附录 A 的 A2（SSE 连接泄漏）在群聊场景下会变得更严重——群聊中每个成员可能打开多个 SSE 连接，如果没有 per-uid 连接上限，单个用户开启大量 SSE 连接到不同 Tab 会放大 `hub` 的内存压力。建议在群聊之前先把 A2 处理掉，或者在方向三（端点级限流）中对 SSE 的并发连接加以限制。
