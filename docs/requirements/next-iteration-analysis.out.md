## 几个补充观察

1. **方向三（数据导出+账户删除）的复杂度被轻微低估了**
   - 级联删除涉及的文件、消息、评论、通知、偏好、block 关系、role 分配——每张表都需要在 `service` 层编排事务边界。现有的 `repository` 层每张表独立操作，跨表事务需要 `*gorm.DB` 透传或使用 `outbox` 驱动异步级联。
   - 建议先实现「数据导出」（相对隔离），再实现「账户删除」——后者的测试需要覆盖大量边界。

2. **方向二的 `user_bans` 中间件位置**
   - 根据现有架构（`middleware` → `handler` → `service`），封禁检查应放在 **`middleware` 层**（`AuthMiddleware` 之后、路由分发之前），而不是 service 层。因为被封禁用户连 SSE 连接都不应该被接受，且在所有 handler 前拒绝可以避免多层重复检查。
   - `middleware` 已经有一个 `RateLimitMiddleware` 模式可以复刻。

3. **性能优化 #2（SSE断线续连索引）**
   - 当前索引 `idx_notifications_recipient_created` 是 `(recipient_uid, created_at DESC)`——这已经覆盖了 `LastSince` 查询（`WHERE recipient_uid = ? AND created_at > ?`），不需要额外索引。这点可以在文档中标注为"已验证"。

4. **快速短期修补中提到的"基础封禁中间件（不实现管理端点）"**
   - 这个权衡值得讨论：有中间件但没有管理 API，意味着封禁只能通过 SQL 手动操作——这会绕过审计日志（`audit_events`），与整个系统的可审计性原则冲突。建议要么一起做，要么用注释标明"必须先通过 `POST /v1/admin/bans` 操作"。
