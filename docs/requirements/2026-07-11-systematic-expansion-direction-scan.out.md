这是一份非常全面且深入的分析。我已经通读了全部内容，以下是我的反馈：

## 整体评价

这份扫描的质量很高——代码级证据引用精准，每个方向都给出了具体的文件行号和代码片段，而不是泛泛而谈。方向选择也很有眼光：它们确实跳过了 70+ 既有文档的覆盖范围，指向的是基础设施层面的**能力空洞**而非功能增量。

## 逐方向反馈

### 方向一（延迟任务框架）— P1 ✅ 强烈认同

这是最核心的缺失。有一个细节值得注意：当前的 Outbox 机制其实**天然承载了**大部分延迟任务的"多消费者"和"重试"语义。如果能复用 Outbox 的 `Events` 模型 + `Dispatcher` 模式 + `Retry` 机制，延迟任务框架的增量实现成本会比想象的低——`scheduled_jobs` 表 + 一个定制的 `Relay`（按 `scheduled_at` 而非 `created_at` 轮询）即可。不建议另起一套 worker 基础设施。

### 方向二（作用域搜索）— P1 ✅

分析到位。有一个潜在的设计决策需要提前做：scope 过滤是在 SQL 层用 `AND` 拼接，还是在搜索服务层做后过滤。我的倾向是 SQL 层解决（性能好），但这意味着需要为不同 scope 组合做复合索引规划——建议提前对常见的 scope 组合做索引覆盖分析，避免建表之后返工。

### 方向三（API Contract）— P2 ⚠️

定位准确但有一个反对意见：**P2 低估了这个问题**。双传输同构是 aero-id 的架构核心承诺，但当前没有工具能确保 HTTP 和 gRPC 的接口语义不漂移。在引入第一个外部消费者之前修复这个问题，成本远低于有了消费者之后。建议至少做 Step 1（OpenAPI 规范）提到 P1，Step 2/3 可以 P2。

### 方向四（合成事务探针）— P1 ✅

极好的点。"false health"场景的描述非常到位。有一个实现层面的注意事项：合成探针如果和真实业务共享数据库，需要考虑测试数据残留的清理策略。建议参考文中提到的 `monitor_` 前缀 uid + 独立的存储隔离空间，并且探针本身应该有超时和断路器——最坏的情况是探针本身出问题导致误报。

### 方向五（Async Context Propagation）— P2 ⚠️

同样存在优先级低估的风险。在当前的生产环境中，**outbox 是核心可靠性的瓶颈**——任何通知/推送/webhook 的故障排查都要靠日志时间戳手动关联。如果生产事故发生在 outbox relay 失败时，`context.Background()` 意味着你看到的是孤立的 traces，完全无法回溯到触发该 outbox event 的原始 API 请求。建议至少对 outbox（最关键的异步路径）**提升到 P1.5**，sweeper 和 cleaner 可以 P2。

## 额外建议

在阅读方向一的分析时，注意到一个问题：现有的 outbox event 和 scheduled_job 如果并存，需要明确**两者的职责边界**：

| 特性 | Outbox Event | Scheduled Job |
|------|-------------|---------------|
| 触发方式 | 事务写入 → 立即/近实时消费 | 按 scheduled_at 到期消费 |
| 重试 | 支持（指数退避） | 需要支持 |
| 因果依赖 | 是数据库事务的"副作用" | 独立于任何事务 |
| 消费者 | 通常是 1 个（通知/webhook） | 可以是多个（撤回+清理+通知） |
| 预计延迟 | 秒级 | 分钟到天级 |

如果职责不清晰，很容易出现"用 outbox 做延迟任务"的临时方案，或者"用 scheduled_jobs 做 outbox 替代品"的设计混淆。建议在实现文档中给出决策树。

## 一个可能的遗漏方向

*（不确定是否需要补充到 ROADMAP 中）* 遍历了所有包后，注意到 `internal/config/` 的配置加载是**全量 startup 加载**，不支持运行时热重载（`config.yaml` 的变更需要重启进程）。虽然不是阻塞性缺陷，但在需要动态调整限速阈值、日志级别、SSO 超时等场景下，重启有业务中断成本。可以考虑作为一个 P3 基础设施方向。
