这是一个非常扎实的战略规划文档。我完整阅读了。

几点观察：

### 1. 文档质量很高
方向定义清晰，每个方向都覆盖了"Why now"、"架构影响"、"边界情况"——这正是 AGENTS.md 里强调的服务层思维（业务逻辑 + 边界判断）。特别是方向 1 提到了 `group_messages` 表与现有 `messages` 表的共存策略，方向 2 意识到 `storage_refs` 表（migration 000021）可以复用——说明代码扫描很到位。

### 2. 实施顺序我基本认同，但有一个可讨论的点

你给的顺序是 **P0 防滥用 → P1 群组+文件 → P2 Webhook → P3 多租户**，逻辑上没问题。但考虑到**方向 1 和方向 2 都涉及表结构变更（新增列/表）**，如果方向 3 的"分层限流"需要扩展 `middleware/ratelimit.go` 的配置模型，这三者同时开发时可能会有 migration 冲突。建议：

- 如果三个方向并行开发，先合并两个 PR：方向 3（纯配置 + middleware 层，无 schema 变更）永远先合入 main；
- 方向 1 和 2 的 schema 变更走同一次 migration batch，避免 migration 编号冲突。

### 3. 方向 4（Webhook 平台）和方向 5（多租户）有一个隐含的共同依赖

当前 `internal/app` 的 composition root 只有**单 outbox relay**、**单 webhook sender**。如果要支持"每个租户独立配置 webhook 订阅 + 独立事件路由"，方向 4 和方向 5 的组合会产生一个架构复杂度跃迁。建议在方向 4 设计时就预留 `TenantID` 字段（即使当前为 NULL），避免方向 5 启动时重构 webhook 子系统。

### 4. 一个小盲区

五个方向都没有提及**文件/消息的过期策略（TTL/Retention Policy）**。如果方向 1 的群聊有"阅后即焚"或"消息自动过期"需求，这个在群组模型中比单聊更容易引爆合规问题（消息必须在一定时间后彻底删除，不只是软删除）。可以考虑在方向 1 或 2 的边界情况中追加。
