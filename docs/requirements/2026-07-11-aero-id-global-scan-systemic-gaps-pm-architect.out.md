## 逐方向技术审阅

### 方向一：Outbox 事件契约版本化

**代码证据准确度**: ✅ 精确。你指出的 5 处证据全部正确。

**架构深度**: 中上。但你忽略了两个关键的既有基础设施：
1. **Webhook 已有 `X-Hub-Signature-256` HMAC 签名** — `internal/outbox/webhook.go` 的 `signPayload`。签名本身不能替代 schema versioning，但说明团队已经考虑了 webhook 消费者验证问题。
2. **死信机制已就位** — `outbox_events.retry_count` 和 `max_retries`。这意味着 schema 变更**至少有两阶段部署窗口**（旧消费者消耗旧事件 + 死信队列切换）。

**真正的缺口**不在于"完全没有 schema versioning"，而在于**没有提供消费者协商能力**（无 `GET /v1/admin/events/schemas`、无 `Accept-Version` header 支持）。建议聚焦于此。

**PM 视角**: ✅ 合理。但优先级可以降为 P2 而非 P1——在外部队列消费者出现之前，这不是阻塞性问题。今天 schema 变更只需协调部署窗口即可。

### 方向二：搜索 Cursor 分页与范围限定

**代码证据准确度**: ⚠️ 有重要遗漏。

你只分析了 `SearchService.Search` 的 `limit` 参数缺少 cursor，但遗漏了三个关键事实：

1. **ts_rank 排序使 cursor 分页极其脆弱** — `ts_rank` 值会因为新插入文档而变动（总文档数影响 IDF）。`(ts_rank, id)` 复合 cursor 在并发写入下会产生**结果漂移**（同一页在不同时间翻页可能看到不同文档）。Offset 分页对搜索其实更合适。

2. **SearchScope 已在 proto 中被占位** — `api/proto/aero_id/v1/aero_id.proto` 虽然没有非搜索的 scope 字段，但 `kind` 枚举已经是范围限定的雏形。你的建议方向对，但没引用 proto 中已有的结构。

3. **跨实体搜索结果拼接无全局排序** — 你只说了"没有 cursor"，但更严重的问题是消息、评论、文件的结果按 `append(kind)` 顺序排列，而不是按统一的相关性分数归并。这是一个排序语义 bug。

**PM 视角**: ✅ 极强。搜索不能翻页是用户可见的 UX 缺陷。建议 P1 保留。
