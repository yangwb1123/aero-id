### 1.2 关键冲突与调和

**冲突1: D4/D8 文件预处理管线 — 两种设计哲学**

| 维度 | 文档A (§4) | 文档B (§3) |
|------|-----------|-----------|
| 任务调度 | 自建 `file_processing_jobs` 表(outbox风格) | 复用 outbox (`file.uploaded` 事件 → worker) |
| 状态追踪 | job 表 + status 字段(独立生命周期) | `File.Meta` 内嵌处理状态 |
| 推荐的扩展点 | 自建 Worker 轮询 job 表 | outbox relay 驱动管线 |

**调和建议**:

两套方案本质上是同一架构选择的两端：**文档B的 outbox 方案更轻量**（无需新表、不引入 Worker），**文档A的 job 表方案更鲁棒**（独立追踪、重试、dead-letter）。建议**采用分层方案**：

```
Phase 1 (Sprint 1): 文档B方案 → outbox 驱动，file.meta 记录结果
Phase 2 (Sprint 3+): 文档A方案 → job 表作为 outbox 的下游消费者
                        (outbox → job 表 → worker handler)
```

理由：outbox 是最小可行路径，1-2天可交付缩略图；job 表解决重试可见性、失败原因、手动重放等运营需求，属于后增保障。

**冲突2: D2 vs D8 — 会话模型 vs 对话聚合**

文档A的 D2(会话模型统一)与文档B的 D4(对话聚合列表)不是竞争关系而是**上下游关系**：

```
文档B D4(对话聚合) ← 依赖于 ← 文档A D2(会话模型)
```

没有 `conversations` 表，`DISTINCT ON` 聚合只能在消息层面硬算，代价是：
- 无法存储会话级别元数据(置顶、静音、头像)
- 无法支持阅读跟踪(成员级 `last_read_at`)
- 无法支持群组(群组与会话是同一抽象)

**调和建议**: D8 作为 D2 的子任务实现。实施顺序：D2 建表 → D2 backfill 历史数据 → D8 聚合查询(建在 `conversations` 之上)。

## 二、架构评估

### 2.1 当前架构的优势

经过对两文档的代码引用验证，确认 aero-id 当前架构有以下优势：

| 优势 | 证据 | 归属 |
|------|------|------|
| **干净的分层** | handler → service → repository 严格单向，service 聚合所有业务逻辑 | 架构规则 |
| **双传输层互备** | HTTP + gRPC 38 个 RPC/5 个服务，行为经 `test/dual` 验证 | 代码结构 |
| **事务性 outbox** | 写路径使用 outbox 保证通知/事件可靠投递，是生产级模式 | 架构模式 |
| **软删除一致** | GORM `DeletedAt` 遍布所有实体，查询内置 `WHERE deleted_at IS NULL` | 数据层约定 |
| **存储抽象** | `FileStorage` 接口隔离开 local/S3，通过 DI 切换 | 抽象设计 |
| **SSO 隔离** | 无账号表、无自签发 token，身份完全委托 SSO | 安全边界 |
| **审计全面** | 7 种已记录事件类型，管理员可跨用户查询审计日志 | 合规基础 |
| **可观测性** | OTel + RED 指标 + 按依赖 readiness 检查 + 优雅关闭 | 运营就绪 |

### 2.2 关键架构债务

按严重度排序：

#### 债务 1: 死代码包 (P0) — 跨文档确认

两文档均未主动定位，但 `internal/notification/`(1516行) 和 `internal/search/`(538行) 是完全未使用的死代码包。 `make check-file-sizes` 不检查死代码，但每次编译/测试都包含它们。

**影响**: 增加构建时间、误导新开发者、度量失真(代码覆盖率虚低)。

**修复**: 删除这两个包(或标记 `// Deprecated — will be removed in v2`)，但需确认 `internal/search/` 中是否有 `service/search.go` 依赖的测试 fixture。

#### 债务 2: 文件分享未考虑屏蔽 (P1) — 文档A附录A4 确认

`fileService` 中无 `BlockChecker`，`canRead()` 不检查请求者与 owner 之间的屏蔽关系。

**影响**: 被屏蔽方可能通过文件分享绕过屏蔽——安全模型缺口。

**修复**: 向 `fileService` 注入 `BlockChecker`，在共享路径 `IsSharedWith` 之后追加屏蔽检查。

#### 债务 3: per-instance 状态 (P1) — 文档B §2 确认

限流器、idempotency store、SSO 缓存、通知折叠均在内存中，多实例部署时各自为政。

**影响**: 扩缩容影响限流效果、蓝绿部署时 key 不共享、通知折叠失败。

**修复**: 渐进式 Redis 引入(文档B 推荐方案 Phase A→D)。

#### 债务 4: 引用计数不完整 (P2) — 文档A 附录A1 确认

文件去重路径中，`files.Create` 与 `refs.Increment` 不在同一事务内，崩溃时可能导致引用计数泄漏。

**影响**: 存储 GC 可能错误回收仍被引用的文件，或漏回收已无引用的文件。

**修复**: 将 `refs.Increment` 纳入 `files.Create` 的事务边界。

#### 债务 5: 通知折叠时间覆盖 (P2) — 文档A 附录A2 确认

折叠时 `existing.CreatedAt` 被覆盖为 `time.Now().UTC()`，改变通知的原始创建时间，可能干扰排序。

**影响**: 通知列表按创建时间排序时，折叠后的通知位置漂移。

**修复**: 折叠时保留最早 `created_at`。

### 2.3 架构约束合规性

| 约束 | 限值 | 两文档的分析文件 | 结果 |
|------|------|-----------------|------|
| 文件 ≤ 500 行 | 500 | 文档A 612行 + 文档B ~300行 | 文档A **超标** 112行 |
| 函数 ≤ 50 行 | 50 | N/A(分析文档，无函数定义) | — |
| 复杂度 ≤ 10 | 10 | N/A | — |

**注意**: 文档 A 本身 612 行，超过 500 行限制。作为分析文档不属 `make check-file-sizes` 范围，但应考虑拆分(建议分成 5 个独立方向文件)。

## 三、高价值扩展方向 (合并后)

基于两文档的重叠分析和依赖关系梳理，合并后得到 **7 个独立方向**：

### 方向 1: 内容安全与滥用防御体系 ⭐⭐⭐⭐⭐

| 维度 | 内容 |
|------|------|
| **业务价值** | 法律合规(非法内容发现)、用户体验(反垃圾)、平台声誉 |
| **技术价值** | 补齐安全模型"预防"环节，形成"预防→限流→检测→处置→审计"闭环 |
| **核心挑战** | (1) 无外部 NLP/ML 依赖下的 Spam 评分有效性；(2) 误判对用户体验的伤害 |
| **预期变更** | `user_sanctions` 表 + `internal/content` 新包(评分/匹配) + admin 制裁端点 + middleware 整合 |
| **对现有影响** | 低 — 新包+新表，不修改现有业务 handler；需在 middleware 层追加制裁检查 |
| **实现路径** | 1) Spam 评分规则(纯 Go 规则引擎) → 2) admin 制裁端点 → 3) 管理制裁整合 → 4) 文件扫描(ClamAV) 后置 |

### 方向 2: 文件预处理管线 ⭐⭐⭐⭐⭐

| 维度 | 内容 |
|------|------|
| **业务价值** | 产品体验刚需(缩略图预览)、带宽节省、搜索覆盖文件内容 |
| **技术价值** | 引入异步任务管线模式(可复用给未来方向) |
| **核心挑战** | (1) 处理延迟与上传完成之间的一致性；(2) 缩略图存储成本与 GC 策略 |
| **预期变更** | `file_processing_jobs` 表 + 管线 Worker + `thumbnails` 存储路径 + API 端点 |
| **对现有影响** | 低 — 独立 Worker 进程，不修改上传主路径；`File.Meta` 已有扩展空间 |
| **实现路径** | Phase 1: outbox 驱动(文档B方案) → Phase 2: job 表(文档A方案) → 迭代追加缩略图/OCR/EXIF/扫描 |

### 方向 3: 审计告警与异常行为检测 ⭐⭐⭐⭐

| 维度 | 内容 |
|------|------|
| **业务价值** | 安全运营闭环(SOC2/ISO27001 合规)、内部威胁检测、成本控制 |
| **技术价值** | 规则引擎模式可复用(如未来用于配额告警、费率告警) |
| **核心挑战** | (1) 窗口计数器性能(大量并发事件)；(2) 告警风暴抑制(冷却机制) |
| **预期变更** | `alert_rules` + `alert_events` 表 + 规则匹配器(异步) + admin 告警端点 + 通知集成 |

| **实现路径** | 规则引擎内核(窗口计数器) → 内置规则模板 → admin 管理端点 → 告警通知集成 → 冷却/去重 |

### 方向 4: Redis 共享状态 (分布式基础设施) ⭐⭐⭐⭐

| 维度 | 内容 |
|------|------|

| **技术价值** | 消除 per-instance 架构瓶颈，是支撑其他方向(群组、Webhook)的弹性基础 |
| **核心挑战** | (1) Redis 成为新故障点(需 fallback 策略)；(2) 迁移过程中双轨运行复杂度 |

| **实现路径** | Phase A: Idempotency(Redis) → Phase B: Rate Limiter → Phase C: SSO 缓存(多级) → Phase D: Outbox 租约 |

## 四、接口设计建议

### 4.1 原则

基于两文档中暴露的设计模式，提炼以下接口设计原则：

1. **服务层是唯一逻辑源** — handler 不判断业务条件(如"是否屏蔽"、"是否有权编辑")，service 统一处理并返回 `AppError`
2. **配置是策略，代码是机制** — 可变的策略(表情列表、Spam 阈值、告警规则模板)走配置/TOML；不可变的逻辑走代码
3. **新增不破坏旧有** — 新端点/新表先于旧端点/旧表上线，`expansion-directions.md` 和附录 A 多处强调向后兼容
4. **异步管线统一采用 outbox 模式** — 所有异步任务(缩略图、内容扫描、告警匹配)统一从 outbox 事件驱动，而非各自建调度器

### 4.2 关键新抽象层

| 抽象层 | 理由 | 适用方向 | 设计要点 |
|--------|------|---------|---------|
| `ContentScanner` (interface) | 隔离扫描后端(ClamAV / 第三方 API / 本地规则) | 方向1(内容安全) | `Scan(ctx, reader) -> (ScanResult, error)`；可注入 mock |
| `SpamScorer` (interface) | 隔离 Spam 评分策略(规则 vs ML) | 方向1(内容安全) | `Score(ctx, content, meta) -> (int, reason)`；策略可插拔 |
| `Processor` (interface) | 统一文件预处理 handler 签名 | 方向2(文件预处理) | `Process(ctx, fileID) error`；不同 job_type 各自实现 |
| `RuleMatcher` (interface) | 隔离告警规则匹配引擎 | 方向3(审计告警) | `Match(ctx, event) -> []AlertTrigger`；支持热加载 |
| `ConversationStore` (interface) | 隔离会话存储(可能需支持不同 backfill 策略) | 方向5(会话模型) | `Create/Get/List/UpdateLastMessage`；事务要求高 |

### 4.3 向后兼容策略

| 场景 | 策略 | 例子 |
|------|------|------|
| 数据模型变更 | 新表先写，旧表只读到迁移完成 | 表情反应：`emoji_reactions` 写 + `comment_likes` 读 |
| API 端点变更 | 旧端点标记 `Deprecated` 头，新端点上线后再灰度弃用 | 收件箱：`GET /v1/inbox` 保持，新增 `GET /v1/conversations` |
| 参数默认值 | 新增参数有默认值(如 `reaction_type` 默认 `'like'`) | `ReactToMessage(actor, msgID, reactionType="like")` |
| 存储接口扩展 | `FileStorage` 接口新增方法时提供默认实现(embed struct) | 缩略图路径非必须，不存在时走原图降级 |

## 五、技术选型评估

### 5.1 新依赖引入决策

| 候选技术 | 方向 | 推荐 | 理由 |
|---------|------|------|------|
| **Redis** | 方向4(共享状态) | ✅ **强烈推荐** | 架构刚需；Go 生态成熟(go-redis/rueidis)；无替代方案(分布式约定需要共识存储) |
| **ClamAV** | 方向1(文件扫描) | ⚠️ **条件推荐** | 开源、Go 有 `go-clamav` 客户端、容器化易行；但更新病毒库需要额外运维。**替代方案**: 第三方 API(VirusTotal)但涉及成本和数据隐私 | 
| **imaging / vips** | 方向2(缩略图) | ✅ **推荐 imaging** | `github.com/disintegration/imaging` 纯 Go、无 CGo 依赖；vips 性能更好但有 CGo 负担。对于 aero-id 的预期规模，imaging 足够 |
| **ffmpeg** | 方向2(视频缩略图) | ✅ **推荐** | 业界标准，但需考虑二进制依赖和进程管理。建议封装为 `ffmpeg.Subprocess(ctx, args)` |
| **OCR (tesseract)** | 方向2(文字提取) | ⏸️ **延后** | 高复杂度、高资源消耗、收益不确定。建议作为方向2的 Phase 3 再评估 |
| **NLP/反垃圾 API** | 方向1(内容安全) | ⏸️ **延后** | Spam 评分初期用纯规则(正则、频率、重复检测)足够，误判率可控后如有余量再引入 ML |

### 5.2 自建 vs 采购决策框架

适用于方向1(文件扫描)和方向7(Webhook 集成)：

| 组件 | 自建方案 | 采购方案 | 推荐 | 理由 |
|------|---------|---------|------|------|
| 文件恶意扫描 | ClamAV(开源，自运维) | VirusTotal API(按量付费) | **自建** | 数据不离开内部网络、合规优势；ClamAV 社区活跃 |
| Spam 检测 | 规则引擎(Go + 正则) | 第三方 API(AWS Comprehend, GCP NLP) | **自建** | 无敏感数据外泄；规则引擎可渐进增强；MVP 只需重复检测+频率 |
| 告警通知 | 复用现有 NotificationDispatcher | PagerDuty / OpsGenie | **自建** | 已有通知基础设施，增量成本低；通知目标是站内 admin 而非外部 |

### 6.3 风险矩阵

| **Redis 引入导致运维复杂度增加** | 高 | 中 | 使用托管的 Redis(ElastiCache/Upstash)；所有操作降级为内存模式(配置开关) |

## 七、对两文档的逐项补充意见

### 7.1 对文档A的补充

| 章节 | 补充意见 |
|------|---------|
| §1 多表情 | 应考虑 `reaction_type` 的顺序可配置(如"热门表情"前置)；Slack 的自定义表情(emoji 别名)是否未来需要？建议 `reaction_type` 设计为可扩展字符串而非枚举 |
| §2 会话模型 | 缺少 `conversation_members.role` 的 `'direct'` 角色语义(1:1 中双方是否都是 admin？)；建议 direct 双方 `role = 'member'`，无 admin |
| §3 内容安全 | Spam 评分规则应支持配置文件热加载(无需重启)；`user_sanctions` 的 `sanction_type` 建议加 `'shadow_ban'`(用户感知不到被限流) |
| §4 文件预处理 | 缺少文件格式转换的讨论(如 HEIC→JPEG 兼容)。建议设置 `allowed_upload_types` + 服务器端 `convert_format` 配置 |
| §5 审计告警 | `alert_rules` 的 `scope` 建议增加 `'subject_type'`(如监控某类实体的删除操作)；cooldown 应以规则为单位而非全局 |
| 附录A | A1(引用计数竞争)应加 **P0** 标签；A5(Block+群组)应在方向5实施时作为 checklist 项；A8(replier_uid 缺失)影响通知显示，建议优先级提到 P1 |

### 7.2 对文档B的补充

| 章节 | 补充意见 |
|------|---------|
| §1 群组消息 | 应考虑群组"自动离开"场景(SSO 账号删除时，需通过 outbox 订阅 `user.deleted` 事件来触发群组成员移除) |
| §2 Redis | Phase A 中 idempotency key 的 TTL 设置策略需要明确(当前 GORM 表的 TTL 是隐式的、基于应用层 GC)。建议显式 TTL = 业务上最大重试窗口(如 24h) |
| §3 文件预处理 | 管线 worker 的资源隔离应考虑(CPU 密集的缩略图生成不应影响 API 延迟)。建议 Worker 作为独立进程部署，或者用 cgroups/容器限制 |
| §4 对话聚合 | `DISTINCT ON` 查询在 `messages` 表百万级时性能退化，建议先用 `EXPLAIN` 验证。如有问题→改用物化视图或 `conversations` 表(即文档A D2方案) |
| §5 Webhook 平台 | 签名密钥轮换协议建议参考 Stripe/Svix(双密钥窗口：新旧密钥在过渡期同时有效)；这将影响 `WebhookHandler` 的签名验证逻辑 |

## 八、总结

### 8.1 最终优先级排序

```
P0 ── 死代码清理 + 引用计数修复 + 文件分享+屏蔽
P1 ── 内容安全(Spam) + 审计告警(内核) + Redis(idempotency) + 缩略图
P2 ── 会话模型统一 + 多表情反应 + Redis(限流+缓存+outbox)
P3 ── 群组消息 + Webhook 平台
```

### 8.2 两文档关系总结

- **文档A** (2026-07-10) 偏产品/UX视角：5 个方向中有 3 个(多表情、内容安全、审计告警)是文档B完全未涉及的，补了重要空白
- **文档B** (expansion-directions.md) 偏基础设施/平台视角：Redis 共享状态和 Webhook 平台是两个关键的基础设施方向，文档A未覆盖
- **重叠区域** (文件预处理、会话)中，文档A提供了更完整的数据模型设计，文档B提供了更轻量的管线模式
- **综合优先级** 建议将内容安全(文档A独家)和 Redis 共享状态(文档B独家)作为 Phase 1 双主线并行推进
