# aero-id 架构分析

## 1. 架构评估

### 1.1 优势

**分层清晰且可测试。** 依赖方向是严格的单向：handler → service → repository/storage/sso。这为每个层级的独立测试提供了干净的支持——服务层使用该层声明的接口进行测试，并使用模拟依赖项（`internal/service/mocks`）。我在 `app.go` 中看到的组合根是每层之间隔离的良好证据；没有包跳过层级。

**事务性发件箱模式（`internal/outbox`）是经过深思熟虑的决策。** 副作用与导致它们的数据在同一数据库事务中写入，然后由中继异步消耗。这使得通知传递、webhook 递送和计数器的可靠性从尽力而为提升为有保证的语义，而无需两阶段提交。回退和死信处理的存在（`DefaultMaxRetries = 20`，指数退避，上限为 1 小时）表明这是一种生产就绪的心态。

**双传输共享同一业务逻辑层。** HTTP（Gin）和 gRPC 都调用 `service` 包中的相同接口。这确保了 REST API 和 protobuf 服务的行为相同——这一领域在很多系统中是薄弱的。`internal/handler/http` 和 `internal/handler/grpc` 都有针对传输级关注点的测试。

**每 UID 分片的 SSE Hub（`internal/hub`）。** 每个用户的订阅存储在自己的 `uidSubs` 互斥体下。这意味着发布到 Alice 绝不会阻塞订阅或发布到 Bob。通道缓冲（16 个事件）和对于慢速消费者的非阻塞发送是事件流的合理默认设置。

**用于存储 GC 的原子引用计数（`storage_ref`）。** 存在 `storage.RefCounter` 接口，它能安全地处理并发内容去重上传与清除扫描之间的竞态条件。这表明了对并发问题的深思熟虑。

### 1.2 局限性

**不存在可观测性插件。** `internal/pkg/db/db.go` 配置了基本的 GORM，但没有 OpenTelemetry 插件。这意味着对于数据库查询持续时间在追踪中是不可见的——只有来自 `internal/pkg/tracing/tracing.go` 的 HTTP/gRPC 范围的可见性。`metrics.Registry`（基于 Prometheus）记录了 RED 指标，但缺失了数据库层面的指标。这是一个低投入高回报的改进。

**限流器是每实例的（`internal/pkg/ratelimit`）。** 如其文档所述，令牌桶保存在进程内存中。在多个副本下，如果流量分布不均匀，限流变得不一致。对于协调限流，需要 Redis 或类似后端——但这增加了操作复杂性。对于大多数场景，每实例的限流已经足够；这是一个需要根据业务需求做出的有意识的权衡。

**SSO 缓存是内存型的。** 令牌缓存（`internal/sso/token_cache.go`）和用户信息缓存（`internal/sso/user_cache.go`）都是受 `sync.RWMutex` 保护的 `map[string]...`。在多副本部署中，每个实例都有自己的缓存，缓存未命中率与副本数量成正比，并且失效模型（基于 TTL）意味着最终一致性。除非缓存大小灾难性增长，否则这不是问题，但值得记录。

**存储 GC 的 `Start` 方法使用 `context.Background()`。** 在 `internal/storage/gc/sweeper.go:213` 中，传递给 `s.Run(ctx)` 的 `ctx` 是 `context.Background()`。这意味着 GC 传递无法通过应用级关闭来取消——它只能通过 `stopGC` 函数来停止。这与 `outbox.Relay.Start` 的模式相同，所以这并非不一致，但它意味着在关闭过程中，GC 扫过可能已经被部分关闭的存储后端的情况存在一个微小的窗口。

**`app.go` 持续增长。** 该文件有 516 行，超过了我之前看到的 500 行上限。在每次添加新服务/存储/依赖项时，它都会增长。这是架构债务的第一个触发点。组合根需要被拆分为负责不同关注点（存储、SSO、后台任务、传输）的可组合函数。

### 1.3 架构债务

| 债务 | 代码依据 | 影响 | 建议 |
|--------|-----------|------------|----------|
| `app.go` 超过 500 行 | 516 行 | `New()` 函数成为了所有依赖项的大型列表，难以推理新增内容的间接影响 | 将 `New` 拆分为 `initStorage()`、`initSSO()`、`initServices()`、`initBackgroundJobs()` |
| `PermUserBan` 已定义但未使用 | `internal/domain/admin.go:9` | 领域语言承诺了不存在的能力。这是个陷阱。 | 要么实现用户封禁 API（+ 写时拦截），要么移除此常量直到构建此功能 |
| S3 的下载器为 nil（`app.go:265`） | `return s3, nil, nil` | S3 后端无法提供与本地存储相同的签名验证下载路径。这不是 bug（S3 直接提供预签名 URL），但意味着文件处理函数需要处理 `nil` 下载器 | 为 `GetDownloadURL` 添加传输层职责分离——本地提供 HMAC 验证的端点，S3 直接返回预签名 URL |
| 多个包结构不匹配 | `internal/comment/` 与 `internal/service/comment.go` 共存 | 新旧服务布局混合（`comment/`、`message/`、`file/`、`block/`、`notification/`、`search/` 是独立包，但 `internal/service/` 也有 `comment.go`、`file.go` 等） | 统一迁移到 `internal/服务层/` 或记录过渡状态。目前这是一个误导性的导航问题 |

## 2. 扩展方向

### 方向 A：多租户支持

**为什么需要？** aero-id 目前假设一个平面命名空间：每个 SSO UID 属于一个隐含的组织。如果业务需要隔离的租户（独立的数据集、独立的管理员、独立的配置），租户概念需要在数据模型和执行路径中体现。

**核心挑战：**
- 所有表都需要 `tenant_id` 列和复合索引，且不能破坏现有数据的向后兼容性（所有行都获得系统租户 ID）
- 授权检查必须在每个操作开始时验证租户成员资格——在 Actors 上下文中添加 `tenant_id` 是单向的，但服务层全局性也需要它
- SSO 集成需要传播租户上下文；要么 SSO 返回租户成员资格，要么 aero-id 维护一个单独的租户-用户映射表

**预期的架构变更：**
- 全局 `TenantID` 类型，嵌入到每个领域实体中
- 将 `WithActor(ctx, uid)` 扩展到 `WithTenant(ctx, tenantID, uid)`；或者使用可选的租户包装器
- 每个仓库查询中的租户隔离 WHERE 子句——要么通过中间件 GORM 插件自动注入，要么通过显式的 repository 方法参数
- 租户感知的缓存层（SSO 用户缓存、令牌缓存按租户分片）

**对现有系统的影响：** 巨大。这会影响每一行 SQL、每个服务方法、每个缓存键。它必须是采用向后兼容默认值的增量迁移（例如，`WHERE tenant_id = ?` 中的 `?` 默认为系统租户）。这不是路线图上的 P0，但早在它成为第 N 个租户的瓶颈之前就应该规划好。

### 方向 B：内容审核管道（从被动变为主动）

**为什么需要？** 正如审核文档正确指出的那样，评论审核目前是被动的（标记然后手动审核）。缺失的是**自动扫描**：病毒扫描、NSFW 图片检测、垃圾内容分类。没有这个，平台会累积有毒内容，直到人工审核员看到它。

**核心挑战：**
- 上传时文件扫描：扫描需要增加上传延迟。同步还是异步？如果异步，未扫描的文件在扫描完成前就不应公开
- 外部扫描服务调用（ClamAV、AWS Rekognition、自定义 ML 端点）是远程依赖项——它们可能失败、超时或返回不可预测的结果
- 自动审核行动（隐藏、标记、删除）以及用户被封禁需要沿着聚合边界进行推理——隐藏评论会影响缓存、通知、SSE 推送
- 需要一个 `message_reports` 表（目前缺失），以及文件上传的扫描生命周期字段

**预期的架构变更：**
- 一个新的 `internal/scan` 包，抽象出扫描提供程序
- 在 `file` 和 `message` 服务中的上传路径处插入钩子（通过扫描服务的 optional interface）
- 扫描队列：如果不希望内联扫描，则使用另一个发件箱变体或专用队列
- 审核工作台：基于角色的端点，用于查看、解决和审核自动标记的内容
- `StorageRef` / `File` 生命周期：一个 `scan_status` 列（待定/干净/恶意/错误），能在上传飞行中阻止公开读取

**对现有系统的影响：** 中等。文件服务（`internal/service/file.go` 和 `internal/storage`）需要扫描集成，但可以将其作为可选的装饰器。评论服务（`internal/service/comment.go`）已经有 `Hide`/`Unhide`——添加自动隐藏直接了当。消息审核（`message_reports` 表）则是全新的基础设施。

### 方向 C：文件版本管理

**为什么需要？** 在审核文档中被列为方向 3。对于作为资产管理的文件（头像、附件、文档），能够替换/回滚版本是强大的能力。没有版本管理，替换就是具有新的 ID 和对所有引用者的级联影响（需要 GC）的新上传来完成清理。

**核心挑战：**
- 版本模型：每个 `file.id` 构成一个版本系列，由共享 `file_group_id` 连接。版本系列是明确的，还是由名称 UID 和存储桶隐式确定？
- 共享语义：我共享了一个版本——如果我上传 v2，接收者看到什么？如果 v2 是私密的呢？
- GC 适配：旧的 blob 被版本替换，但仍然存在引用——按引用计数保留，以便版本系列可以回滚
- 乐观并发：如果 Alice 和 Bob 同时上传替换，谁获胜？需要 `updated_version` 或 CAS

**预期的架构变更：**
- `file_versions` 表（`file_id`、`version_number`、`storage_key`、`size`、`checksum`、`created_at`、`deleted_at`）
- `File` 实体获得的 `current_version` 字段
- API：`POST /v1/files/:id/versions`（上传新版本）、`GET /v1/files/:id/versions`（列表）、`POST /v1/files/:id/versions/:v/rollback`（设为当前版本）
- GC 适配：当没有版本引用时回收 blob（不仅仅是文件行）
- 存储后端适配：`FileStorage.Stat` 用于 S3 预签名验证

**对现有系统的影响：** 中到高。同意审核文档的评估。这需要 2-3 个新表、5+ 个新端点、存储 GC 适配以及关于版本的共享语义的艰难决策。如果文件版本管理不是产品的紧迫需求，那么它就是 P1—P2。

### 方向 D：工作区 / 空间权限

**为什么需要？** 在审核文档中被列为方向 1。当实体（文件、消息、评论）属于一个命名空间时，权限可以在每个命名空间基础上授予，而不需要在每条记录上设置 `owner_uid`。这与多租户相关，但不同——工作区是用户数据的逻辑分组，而不是系统隔离边界。

**核心挑战：**
- 工作区成员资格模型（所有者、编辑者、查看者、邀请者）
- 与现有 ACL 的交互：文件当前是 `owner_uid + visibility`；消息是对话（`from_uid` + `to_uid`）。工作区需要额外的执行路径
- 与审核的集成：审核员应在工作区范围内进行操作，而不是在平台范围内
- 迁移路径：现有数据没有 `workspace_id`。添加时默认设为用户个人工作区

**预期的架构变更：**
- `workspaces` 表 + `workspace_members` 表
- `workspace_id` 列添加到每个实体表中（最初可为空以支持渐进迁移）
- 新的 workspace service 层，处理邀请、角色和成员资格管理
- 授权装饰器：现有权限检查回退到 `owner_uid` 检查，如果实体的 `workspace_id` 为空
- 空间感知的面向用户的 endpoints（例如 `GET /v1/workspaces/:wid/files`）

**对现有系统的影响：** 中高。这触及每个实体和每个权限检查。然而，它与审核管道（方向 B）的耦合比看起来要弱——工作区权限独立于审核队列逻辑。它可以安全地并行进行。

### 方向 E：多区域 / 分布式 ID 生成

**为什么需要？** aero-id 使用 UUIDv7（`internal/pkg/idgen`），它在单个区域内按时间排序。在需要带地理分布式写入的多区域部署中，UUIDv7 如果区域间时钟未同步（或无全球共识）可能会产生冲突。

**核心挑战：**
- UUIDv7 的单调性依赖于单调递增的时钟。在时钟回拨或区域间时钟偏移下，ID 可能不按时间顺序出现，从而破坏分页（`ORDER BY id DESC WHERE id < cursor`）
- 区域间 ID 去重：如果两个区域在相同毫秒内生成冲突的随机组件，你会得到碰撞
- 区域间存储同步：如果 blob 存储在区域特定的 S3 存储桶中，文件引用需要一个区域字段来路由下载 URL

**预期的架构变更：**
- 为 ID 分配添加区域组件：要么是节点 ID 嵌入到 UUID 的变体位中，要么是单独的 `shard_id` 列
- Snowflake 风格的 ID 生成器（数据中心的机器 ID + 序列号）或 Twitter 的雪花算法替代方案
- 分页适配：`WHERE id < cursor` 变成按区域分片，然后在应用层合并
- 存储路由：`File` 实体获得一个 `region` 字段；`DownloadURL` 路由到正确的 S3 存储桶

**对现有系统的影响：** 高。这是一个基础设施层面的变更，影响每个 ID 的生成、每个查询的 WHERE 子句以及每个存储操作。只有在明确的多区域拆分为产品需求之前，才不应实施。在那之前，UUIDv7 对于单区域部署而言是极好的选择。

## 3. 接口设计建议

### 3.1 关键模块的接口设计原则

**服务接口（`internal/service/service.go`）是合适的抽象边界。** 它们定义了传输层（HTTP、gRPC）和业务逻辑之间的契约。每个方法接受一个上下文和一个输入 DTO，返回领域实体和错误。这种模式很好——在添加新功能时保持它。

**对于新包的接口设计原则：**

1. **优先考虑窄接口。** 我看到像 `StorageRefRepository`（`GetCount`）、`RefCounter`（`GetCount`）和 `FileRepo`（用于 GC 的 3 个方法）这样的接口已经在这样做了。继续这种做法——一个接口有 1-3 个方法比一个 15 个方法的全能接口要好。

2. **依赖接口，而不是实现。** `internal/service` 不导入 GORM、`gin` 或 `grpc`。它只导入自己的 DTO 和领域实体。这是正确的做法，必须在所有新代码中强制执行。

3. **为可选的交叉关注点使用装饰器模式。** 审核日志已经这样做了——`AuditLogger` 在服务函数内部是可选调用的。对于扫描、缓存失效和速率限制，我们应该使用相同的模式：可选接口，默认为空操作。

### 3.2 新的抽象层考虑

**考虑添加一个 `pipeline` 或 `middleware` 层用于交叉关注点。** 目前，像审核日志（在服务方法中显式调用 `if s.audit != nil { ... }`）这样的关注点散布在各个代码中。一种统一的方法：

```
// 在写入路径中：

fileSvc := service.NewFileService(...)
fileSvc = pipeline.Wrap(fileSvc,
    pipeline.WithAudit(auditRepo),      // 每个 Create/Update/Delete 前的日志
    pipeline.WithScan(scanService),     // 对新建文件进行自动内容扫描
    pipeline.WithCacheInvalidate(cache),// 在更新后过期缓存条目
)
```

这使关注点与业务逻辑解耦。然而，将每个方法调用包装在装饰器中需要代理——可能是代码生成或反射。对于 Go，简单的显式服务层包装器通常更可取。

**走得更近的替代方案：**

```
// 可选的 interface 注入
type FileLifecycleHooks interface {
    OnBeforeCreate(ctx, file) error    // 返回错误会中止创建
    OnAfterCreate(ctx, file) error     // 日志/审计；失败不会中止
}
```

然后在服务方法中调用 `hooks.OnBeforeCreate`。这类似于现在的 `AuditLogger`，但更加系统化。

**建议：** 继续使用简单的显式模式（`if s.audit != nil`）。对于当前的代码库规模，这种方法的可读性和简单性超过了正式管道抽象的好处。当有 4+ 个横切关注点时，再考虑管道模式。

### 3.3 向后兼容性

**实体演进：** 目前，所有实体都是 Go 结构体。当添加新字段时，它们应该被追加到结构体的末尾，并且 JSON 标签应该保持稳定（不要重命名字段）。对于 gRPC，proto 字段号是用于标识的——永远不要复用或重用已废弃的字段号。

**API 演进：** HTTP API（/v1/前缀下的所有内容）应该遵守：
- 新端点获得唯一的路径
- 现有端点不能改变请求/响应形状而不开新版本
- 查询参数不应被移除，只能添加

**迁移路径：** 对于添加列到领域实体中，使用 `sql.NullString` 或指针类型，以便不破坏从表中读取现有行的能力。这在添加 `workspace_id` 或 `scan_status` 列时特别相关。

## 4. 技术选型

### 4.1 当前技术栈

| 类别 | 选择 | 备注 |
|----------|--------|-------|
| 语言 | Go 1.26 | 在 AGENTS.md 中固定 |
| HTTP 框架 | Gin | 成熟的，正在使用的；对于这个规模没问题 |
| gRPC | google.golang.org/grpc | 标准的，经过验证的 |
| ORM | GORM v2 | 已知的，但 GORM 的查询构建器在不经意间会生成 N+1 查询 |
| 数据库 | PostgreSQL | 未锁定到特定的云提供商 |
| 存储 | Local / S3 (MinIO) | `FileStorage` 接口抽象 |
| 分布式追踪 | OpenTelemetry | 通过 `internal/pkg/tracing` 的基础支持 |
| 指标 | 自定义 Registry + Prometheus | `internal/pkg/metrics` |
| ID 生成 | UUIDv7 (`internal/pkg/idgen`) | 单调排序，无需协调 |

### 4.2 建议的新技术

**用于自动内容审核的 ML 推理服务。** 不要直接嵌入模型（Python → CGo 是没有必要的麻烦）。相反，将扫描卸载到一个单独的服务，通过 gRPC 被调用。aero-id 发送内容（文本、图片元数据），扫描服务返回分类标签。这种分离保持了 CPU 密集型 ML 模型独立于 I/O 绑定的 API 服务器。

- **选项 A：** Google Cloud Vision / AWS Rekognition（托管式，即付即用）
- **选项 B：** Clair（开源容器扫描器）+ 自定义 CLAMAV 包装器用于文件
- **选项 C：** 为自定义 ML 模型自建基于 Triton Inference Server 的微服务
- **建议：** 从选项 A（外部服务，低努力）开始，并在到达规模成本拐点时逐步迁移到选项 C

**用于分布式限流和缓存的 Redis。** 目前，限流器和 SSO 缓存都是进程内、每实例的。对于大规模多副本部署：

- **选项 A：** 保持每实例的限流器和缓存，接受协调一致性的减弱
- **选项 B：** 对限流使用 Redis（`sliding window` 或 `GCRA` 算法），对缓存使用 Redis
- **建议：** 选项 A 适用于 3 个副本以下。在此之上，引入具有带自动发现功能的 Redis 哨兵或集群。不要过早引入 Redis——它增加了部署复杂性。

**用于消息流的 Kafka / NATS。** 目前，outbox 以 5 秒的间隔轮询 Postgres。对于消息吞吐量 > 1000/秒的情况，轮询会成为瓶颈。事件流平台可以卸载轮询并启用真正的发布/订阅语义。

- **建议：** 坚持使用当前的 outbox 模式。该模式没有固定到具体的技术——当 Postgres 轮询变为瓶颈时，`Repository` 接口可以被交换出来，使用 Kafka 消费者 + 幂等 ID 来检测去重。这种情况在路线图上不能早于 P2。

### 4.3 自建与采购的决策框架

对于 new capabilities，使用这个决策矩阵：

| 问题 | 自建 | 采购 |
|---------|------|---------|
| 这是产品的核心差异化因素吗？ | 工作区权限、审核工作台 | 内容扫描 ML、限流后端 |
| 集成有多紧？ | 紧密耦合的（例如文件版本管理） | 松耦合的（例如外部扫描 API） |
| 维护负担？ | 低/中（Go 代码，简单逻辑） | 高（ML 模型漂移、依赖的 API 版本控制） |
| 在路上的成本？ | 更高的前期成本，更高的控制力 | 更高的持续成本，较低的控制力 |

**一般规则：** 构建与你的领域紧密耦合的一切（权限、审核状态机、文件版本管理）。采购与你的领域松散耦合的一切（扫描、限流存储、缓存存储）。

### 5.2 阶段划分

**第一阶段：基础设施稳固（P0）**
- 重构 `app.go` 为 `initStorage()`、`initSSO()`、`initBackgroundJobs()`、`initServices()`、`initTransports()`
- 添加 GORM OTel 插件 + 数据库查询跨度
- 实现 `PermUserBan`（表 + API 路径拦截 + 写入拦截）
- 创建一个 `message_reports` 表，并在写入路径中为 send 添加自动审核标记

**第二阶段：主动审核（方向 B）**
- 定义 `Scanner` 接口（`Scan(ctx, content) → (tags, error)`）

- 扫描队列使用 outbox 变体（或独立的表格）
- 带有手动覆盖和解决流程的审核工作台 API

**第三阶段：高级文件特性（方向 3）**
- 文件版本管理架构（表格 + API）

**第四阶段：工作区和多区域**
- 工作区模型 + 成员资格
- 实体工作区范围界定
- 多区域 ID 生成 + 存储路由
- 分布式缓存 + 限流

### 5.3 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---------|----------|--------|------------|
| 主分支上解锁的 `app.go` 超过 500 行 `make check-file-sizes` | 当前 | 高 | 立即拆分（P0 第一阶段中期） |
| 审核文档中多区域的高估 | 中 | 中 | 延迟多区域，直到它有产品支持；道路图上不要超过 P2 |
| GORM 查询性能在评论/通知规模下退化 | 中 | 高 | 尽早添加数据库查询追踪（GORM OTel），以便退化具有可见性；如果必要，添加查询缓存层 |
| SSO 成为单点故障 | 中 | 高 | SSO 客户端已经有了断路器；添加断路器指标告警。在 SSO 停机期间考虑宽松模式（提供陈旧缓存内容，拒绝写入） |
| 存储 GC 删除正在使用的 blob | 低 | 严重 | 引用计数（`storage_ref`）是保护措施；添加 `GetCount` 检查的集成测试，并验证竞态情况。GC 默认禁用（`Enabled: false`）直到操作员明确启用 |
| 内容扫描延迟使上传变慢 | 中 | 中 | 可选扫描：上传立即返回，扫描在后台进行。未扫描的文件保持 `scan_status = pending`，并被阻止公开访问 |

## 总结

aero-id 拥有稳固的、经过深思熟虑的架构。分层依赖性、发件箱模式以及明确的可选交叉关注点的使用，暗示了具有生产经验的设计师参与。主要弱点集中在：

1. **组合根的规模**——`app.go` 的 516 行使得每次新依赖项的添加都可能成为引人 bug 的碰撞点。这是第一个中优先级项目。
2. **审计/封禁权限未完成**——`PermUserBan` 定义了但未实现。这是领域语言承诺了不存在东西的陷阱。
3. **审核是被动的**——系统可以手动标记和解决，但不能自动扫描。如果平台增长，这是一个产品风险。

路线图从修复 P0 项开始（app.go 拆分、可观测性、用户封禁），然后扩展到自动审核（方向 B），接着是文件版本管理（方向 3），最后是工作区（方向 1）和多区域（方向 E）。对每项改进的工作量评估应通过 `make check-file-sizes && make lint && make test` 进行验证，然后再声称完成。
