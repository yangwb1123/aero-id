# 架构分析：aero-id

## 1. 架构评估

### 核心优势

代码库在分层架构、关注点分离和可操作性方面展示了非凡的设计成熟度。几个突出之处：

**1.1 严格单向依赖。** `handler → service → repository/storage/sso` 法则与代码中的调用图完全匹配。存储库返回原始错误；服务将其转换为 `*AppError`；处理程序对其进行渲染。在两个传输层中没有一次业务逻辑泄露到处理程序中。

**1.2 双协议共享单一服务。** HTTP 和 gRPC 处理程序调用完全相同的 `service.FileService`、`service.MessageService` 等接口。这本质上是防差异的——你在一个地方编写业务逻辑，两个协议端口都获得一致的行为。`parity_test.go` 的存在证实这是有意的、可测试的设计决策。

**1.3 事务性发件箱模式。** 通知传送通过发件箱可靠地进行：领域事件在与生成它们的行相同的事务中写入，然后由中继异步耗尽。这避免了经典的双写问题，而无需分布式事务。该实现（`outbox` 包 + `relay.go`）干净利落地处理了背压、指数退避和死信。

**1.4 SSO 断路器 + 陈旧缓存。** SSO 客户端是一个复杂的状态机：断路器（`breaker.go`）、TTL 限时缓存 + 陈旧缓存（在 SSO 下线时从过期的缓存值中提供数据）、连接池（`dial.go` 中的 keepalive）、重试。这是生产级别的弹性。

**1.5 可选功能的配置哲学——除了一处。** 速率限制、存储 GC、追踪、发件箱 webhook、自动迁移——所有这些功能都有一个 `enabled` 开关，且默认关闭。唯一的例外是幂等性（见下文方向 2），它缺少一个开关。

**1.6 UUIDv7 主键 + 基于游标的分页。** 每个读取路径都通过 `WHERE id < cursor ORDER BY id DESC LIMIT n+1` 实现一致的分页。这是一个经过验证的模式，避免了基于偏移量的分页的陷阱。

**1.7 SSE Hub 按 UID 分片。** Hub 的锁定方案（`sync.Map` over `per-uid mutex`）意味着发布到 Alice 的消息永远不会阻塞订阅或发布到 Bob 的消息。16 个事件的缓冲区用于防止缓慢的消费者阻塞发布者。

### 局限性和技术债务

**1.8 限流器在单个存储桶中混合所有端点。** `RateLimitInterceptor` 和 `RateLimitMiddleware` 共享完全相同的 `*ratelimit.Limiter` 实例。HTTP 和 gRPC 请求消耗同一个每用户存储桶。这意味着一个用户运行资源密集型搜索（每秒来自 HTTP 的 20 个请求）会耗尽他们发送消息的 gRPC 配额。方向一的验证文件正确识别了这一点。文档中未提及的补充边界情况：**HTTP 和 gRPC 之间跨协议竞争**——一个用户可以通过 HTTP 搜索耗尽他们自己的 gRPC 写入容量，反之亦然。

**1.9 幂等性是始终开启的，无法禁用。** 方向二在文件中被正确识别。速率限制、存储 GC、追踪、发件箱 webhook 和自动迁移都有一个 `enabled` 配置键。幂等性则没有。`NewGormStore` 从不返回 nil，并且 `RunCleaner` 总是启动。如果运营商的合规政策禁止存储幂等性密钥，或者如果他们在不需要幂等性的只读副本后面运行，他们无法在不修改代码的情况下关闭它。

**1.10 缺少该单元级别的粒度指标。** 当前指标框架（`internal/pkg/metrics`）记录请求级别的 RED 指标（速率、错误、持续时间）。缺少的是：
- 每个端点每个用户的速率（当前限制的关键维度）
- 存储桶级别的指标（存储桶数量、每个存储桶的平均填充率）
- 每个实体的行数指标
- 发件箱积压指标（深度、最老未发布事件的年龄）

这些对于运营可见性至关重要。

**1.11 Gin 特定的处理程序签名。** HTTP 处理程序的签名是 `func(c *gin.Context)`，这完全没问题且惯用于 Gin。然而，`*gin.Context` 用于通过 `c.GetString("actor_uid")` 获取 actor uid，这意味着处理程序不仅解包请求，还依赖于特定中间件填充的上下文键。一个更清晰的抽象可以通过一个自定义的 `RequestContext` 结构体（填充有 `actor_uid`、`request_id` 等）来实现，该结构体在请求管道开始处构建，但这反映了 Gin 的典型使用模式，而不是真正的设计缺陷。

**1.12 SSE Hub 没有跨实例广播。** `hub.Hub` 是纯内存的。在多个副本后面，发件箱中继在每个实例上本地运行，但 SSE 推送仅到达连接到写入通知的那个实例上的客户端。用户连接到实例 A 不会收到由实例 B 上运行的请求产生的通知。即使方向五的搜索问题正确地被识别，这个问题根本没有在任何方向中涉及——这是一个真正未被发现的间隙。

## 2. 扩展方向

### 方向 A：多实例速率限制 + 端点感知节流（P1）

**为什么需要：** 当前的单实例、单一存储桶限流器是单点瓶颈。在多个副本中，用户可以通过轮换实例来绕过限制。此外，写入密集型端点（上传）饥饿读取密集型端点（搜索、列出）——当前的设计在一个关键维度上缺乏隔离。

**核心挑战：**
- 需要共享状态以进行协调的限流（Redis、Dragonfly 或类似）
- 网络延迟对令牌桶填充的影响（与当前的内存纳秒级操作相比）
- 限流器故障场景：如果 Redis 宕机，我们是开启（允许所有请求，可能使数据库不堪重负）还是关闭（拒绝所有请求，造成停机）？

**预期的架构变更：**
- `internal/pkg/ratelimit` 中的 `Limiter` 成为接口而不是具体类型
- 当前的基于 `sync.Mutex` 的 `bucket` 结构体成为一个实现（`InMemoryLimiter`）
- 添加新的 `RedisLimiter`，使用 Lua 脚本实现令牌桶算法（CAS 操作的最小往返次数）
- 配置获得一个新的 `rate_limit.backend` 键（`memory` 或 `redis`）
- 每个端点路由可以声明一个桶维度（例如，`read_bucket`、`write_bucket`、`sse_bucket`），在中间件中通过请求路径映射

**对现有系统的影响：** 低到中等。`*ratelimit.Limiter` 目前直接在 `app.go`、`router.go` 和 `server.go` 中使用。结构体指针被传递。重构为接口会改变 `New()` 函数签名，但行为在现有代码路径中保持不变。

**竞争设计决策：**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全局存储桶：所有端点在每个用户下一个存储桶 | 实现简单，现有代码 | 读/写饥饿，跨协议竞争 |
| 按端点系列划分存储桶（读/写/SSE） | 良好的维度分离，保护写入免受搜索洪流的影响 | 更复杂，需要端点→存储桶映射，可能会被下游混合工作负载滥用 |
| 按端点系列划分 + 全局上限 | 读/写隔离 + 防止一个用户在每种类型下使用过多 | 最复杂，更多配置旋钮 |

**建议：** 方案 2，按端点系列（读、写、管理、SSE）划分存储桶，映射在中间件层。

### 方向 B：跨实例 SSE 扇出（P1）

**为什么需要：** 当前 `hub.Hub` 是纯内存的。在多个副本后面，SSE 客户端连接到实例 A 永远不会收到实例 B 上产生的通知。这破坏了所有非零数量的副本的实时交付。方向一、三、四、五被涵盖，但**这个跨实例状态问题在任何已分析的方向中都没有被提及**。

**核心挑战：**
- SSE 本质上是每个连接的（WebSocket 连接绑定到一个服务器）
- 跨实例扇出需要每个通知至少有一次数据库往返或一个 pub/sub 中介
- 幂等性：交付至少一次（已经通过发件箱保证）没问题，但需要避免副本之间的重复
- 扩展：100 个并发副本，每个副本有 1000 个 SSE 连接 = 如果每个通知都扇出到每个副本，则产生 100,000 条内部消息

**预期的架构变更：**
- 选项 A：**基于轮询的 SSE**。每个 SSE 连接定期轮询 `notifications` 表以获取给定已见时间戳之后的新行。将 SSE Hub 减少为会话管理，以最少的跨实例基础设施成本实现跨实例交付。
- 选项 B：**基于 Redis Pub/Sub 的扇出**。`dispatcher` 在创建通知行后在 Redis 中发布一条消息。每个实例都订阅该频道并仅在拥有该用户的连接时才将其推送到本地 Hub。添加 Redis 依赖。
- 选项 C：**基于发件箱的跨实例交付**。扩展发件箱中继以将事件推送到每个实例上的本地通知表 + SSE Hub。通知的创建会持久化，中继在所有实例上运行——不需要额外的列基础设施。

**对现有系统的影响：** 中等到高，取决于选项。选项 C 重用现有发件箱基础设施，只需要每个实例的中继消耗本地表中由其他实例创建的行。这最小化了新的基础设施依赖。

**建议：** 选项 C（基于发件箱的扇出）。它将交付与创建解耦，与现有的可靠交付模式相匹配，并且不需要 Redis。

### 方向 C：幂等性配置化 + 可插拔存储后端（P2-P3）

**为什么需要：** 方向二正确地识别了差距——幂等性缺少配置开关。但更深层次的问题不仅仅是 switch：**幂等性存储被硬编码为 PostgreSQL**。速率限制有内存存储；幂等性可以有。对于低容量部署，内存存储足以满足幂等性，并且比数据库往返更快。

**核心挑战：**
- 数据丢失风险：内存存储意味着重启丢失挂起的幂等性密钥——如果发生崩溃，客户端重试可能会重新执行操作
- TTL 管理：内存需要 LRU 驱逐 + 带扫描的 TTL；PG 有 SQL 级过期
- 一致性：幂等性密钥保证需要强一致性。对于单实例来说，内存没问题；对于多实例，需要后端协调

**预期的架构变更：**
- `internal/idempotency` 获得一个配置开关（`idempotency.enabled`）
- 当前 `Store` 接口保持不变，但获得一个新的 `NewMemoryStore()` 实现，类似于 `NewGormStore()`
- `app.go` 根据配置选择适当实现
- 如果启用，Cleaner 运行；如果禁用，则根本不创建 Store，中间件被跳过，不分配 goroutine

**对现有系统的影响：** 低。`Store` 接口已经定义了。添加实现 + 配置开关不会改变现有行为。

### 方向 D：可观察性深度——结构化指标和审计跟踪（P2）

**为什么需要：** 当前指标层记录每个请求的 RED（速率、错误、持续时间，按状态码和方法划分）。缺少的是实时运营所需的业务级指标：存储桶指标（存储桶数量、驱逐率）、发件箱积压跟踪（深度、最老未发布事件的年龄）、SSO 缓存命中率/未命中率、文件上传吞吐量。

**核心挑战：**
- 指标维度爆炸：如果每个存储桶（限流器的关键维度）都进行检测，则基数会爆炸
- 性能开销：带有高基数标签的 Prometheus 可能导致 OOM——需要仔细的标签策略

**预期的架构变更：**
- `metrics.Registry` 获得新的 `GaugeVec` 和 `CounterVec` 方法（或者包裹 Prometheus 客户端库）
- 限流器导出计数：`rate_limit_buckets{state="active"}`、`rate_limit_evictions_total`
- 发件箱导出：`outbox_depth`、`outbox_oldest_unpublished_age_seconds`
- SSO 客户端导出：`sso_cache_hits_total{type="token"}`、`sso_cache_misses_total`
- 存储导出：`storage_upload_bytes_total`、`storage_download_bytes_total`

**对现有系统的影响：** 低。向限流器、发件箱和 SSO 客户端添加仪表化，不会改变它们的行为。指标注册表已经存在。

### 方向 E：搜索索引抽象和平衡限制（P2）

**为什么需要：** 方向五正确地确定了需要每种类型平衡限制和每种类数量。更根本的是，搜索完全基于 PostgreSQL `tsvector`。这很有效，但存在已知的可扩展性限制：联合搜索（跨消息、评论和文件）在 Postgres 中本质上比在专用搜索索引（Elasticsearch、Meilisearch）中更昂贵。

**核心挑战：**
- 在专用搜索引擎中包含每个用户的隔离：当前搜索按 uid 过滤。Elasticsearch 中的文档级安全性（DLS）需要为每个查询添加用户 ID 过滤器，这在规模上很昂贵
- 索引滞后：发件箱驱动的索引同步（事件 → Elasticsearch）引入了几秒钟的延迟。这对于全文搜索来说通常可以接受，但影响 UX
- 资源成本：与 Postgres 相比，运行搜索集群增加了运营开销

**预期的架构变更：**
- `search.Service` 成为接口（当前它已经是，但具体实现是唯一的）
- 添加 `search/postgres.go`（当前实现）和 `search/elastic.go`
- 配置获得 `search.backend`（`postgres`、`elasticsearch`）
- 搜索结果包含每个类别的计数信息（每个搜索的 `per_kind_counts`）

**对现有系统的影响：** 低到中等，取决于后端选择。Postgres 后端继续按原样工作。添加 Elasticsearch 后端是可选的。

## 3. 接口设计建议

### 3.1 重构限流器为接口

当前签名：
```go
func New(rate float64, burst int, idleTTL time.Duration) *Limiter
func (l *Limiter) Allow(key string) bool
func (l *Limiter) RetryAfter() time.Duration
```

必须成为：
```go
type Limiter interface {
    Allow(key string) bool
    RetryAfter() time.Duration
}
```

**为什么：** 这是跨协议竞争（HTTP 与 gRPC）和单实例与分布式限流的解锁模式。`RetryAfter` 在接口中是合理的，因为即使是分布式算法也可以为建议的冷却提供合理估计。

**备选方案：** 目前有一个具体的 `*Limiter` 指针。只需将其切换为接口类型。影响仅限于 `app.go` 和 `server.go` 中的类型 annotations。

### 3.2 保持 Store 接口稳定

幂等性 `Store` 接口是合理的：
```go
type Store interface {
    Reserve(ctx context.Context, uid, endpoint, key string) (*Record, bool, error)
    Complete(ctx context.Context, uid, endpoint, key string, rec Record, ttl time.Duration) error
    Release(ctx context.Context, uid, endpoint, key string) error
}
```

**建议的附加：** `Close()` 方法用于优雅的 Store 关闭（特别是对于 Redis 连接）。当前 `GormStore` 中没有 `Close()`——它依赖于数据库连接在更高级别关闭。

### 3.3 引入 SearchIndexer 接口

当前搜索是具体类型。在将其提升为接口之前不需要新的抽象——它已经满足了一个隐式接口。当添加第二个后端时，一个显式的接口：
```go
type Indexer interface {
    Search(ctx context.Context, query string, kinds []SearchKind, limit int, perKindLimit int) ([]SearchHit, map[SearchKind]int, error)
    // Index and Delete are called by the outbox handler for incremental sync
    Index(ctx context.Context, kind SearchKind, id string, doc any) error
    Delete(ctx context.Context, kind SearchKind, id string) error
}
```

`map[SearchKind]int` 返回每种类计数，解决了方向五。

### 3.4 使用发件箱事件序列化模式

发件箱事件当前使用 `json.Marshal` 负载。这对于同类消费来说很好。对于跨服务集成，基于 protobuf 的模式注册会更好——但不是现在。发件箱 `Event` 结构体有 `AggregateType`、`AggregateID`、`EventType`——这是足够的。

### 3.5 存储层考虑事项

`storage.FileStorage` 接口是合理的：
```go
type FileStorage interface {
    Put(ctx context.Context, key string, reader io.Reader) error
    Get(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
    Exists(ctx context.Context, key string) (bool, error)
}
```

**Missing:** `Stat` 方法用于在不下载的情况下检查对象大小/内容类型，或者列出前缀。当前 `CompleteUpload` 在 S3 上通过 Stat-ing 对象来工作。这在一个接口中很好。

## 4. 技术选型

### 4.1 Redis：何时引入（以及何时不引入）

Redis 的用例在增长，但还没有达到临界点：

| 用例 | 当前解决方案 | 如果引入 Redis | 何时 |
|---|---|---|---|
| 限流 | 内存存储桶 | `RedisLimiter` 使用 Lua | 副本计数 > 3 或限流违规绕过 |
| SSE 扇出 | N/A（每个实例） | Redis Pub/Sub | 副本计数 > 1 且需要实时推送 |
| 缓存 | 内存 + TTL | `RedisCache` 带有陈旧缓存 | 需要跨实例缓存失效或更大的缓存 |
| 幂等性 | PostgreSQL | `RedisStore` 用于低延迟 | 幂等性密钥成为延迟瓶颈 |

**决策规则：** 从内存开始。当副本计数 > 3  **或** 两个不同的运算符报告限流违规绕过（用户在实例之间轮换）时引入 Redis。

**备选方案：** Dragonfly 作为 Redis 的替代品，用于限流（兼容协议，单线程保证的原子性）。

### 4.2 搜索：PostgreSQL 与专用引擎

| 方面 | PostgreSQL tsvector | Elasticsearch / Meilisearch |
|---|---|---|
| 相关性排名 | 基本（`ts_rank`） | 高级（BM25、学习排名） |
| 容错 | 无（与 OLTP DB 相同） | 内置 HA |
| 运营成本 | 0（与 Postgres 捆绑） | 新的集群 |
| 索引延迟 | 即时（同一行） | 秒级（发件箱驱动） |
| 每用户隔离 | 简单（`WHERE owner_uid = ?`） | 需要 DLS（复杂） |

**决策规则：** 保持在 Postgres 上，直到文件计数超过 1 亿 **或** 用户抱怨搜索相关性排名。Postgres `tsvector` 对于 < 1000 万行 3 种类型来说是非常合适的。

### 4.3 当前的 Gin 选择：需要重新评估吗？

Gin 很好。对于这个用例来说没有更好的替代方案。`echo` 或 `chi` 会有不同的中间件签名但相似的能力。没有理由切换。

### 4.4 GORM 与直接 SQL

当前 GORM 的使用是保守的——主要是在单个表上的简单 CRUD，没有复杂的连接。这没问题。如果将来出现跨实体的批量操作或复杂的报告查询，`pgx` 或 `sqlx` 可能更适合这些路径。GORM 不需要被替换——只需要在需要的地方用直接 SQL 路径补充。

## 5. 实施路线图

### 阶段 1：安全性和正确性（P0）——第 1 周

| 项目 | 工作量 | 依赖性 |
|---|---|---|
| **方向 3：** 下载 Content-Type XSS 修复 | 5 分钟 | 无 |
| **方向 4：** 重新排序中间件 + 幂等 429 释放 | 30 分钟 | 方向 3（不相关，可以并行进行） |
| **文档：** 添加 `per_kind_counts` 字段到搜索 | 1 小时 | 无 |

**风险：** 极小。这三个都是具有完全理解的影响的代码更改。

**验收标准：**
- `/files/dl` 设置 `X-Content-Type-Options: nosniff` 和 `Content-Disposition: attachment`
- 幂等性中间件在 `c.Writer.Status() == 429` 时调用 `Release`
- 搜索响应包含 `per_kind_counts` 对象

### 阶段 2：端点粒度限流（P1）——第 2-3 周

| 项目 | 工作量 | 依赖性 |
|---|---|---|
| 按端点系列重构 `*Limiter` → `Limiter` 接口 | 1 天 | 无 |
| 实现读写存储桶映射 | 1 天 | 接口重构 |
| SSE 豁免（无限制的 `/events`） | 2 小时 | 无 |
| 将存储桶指标添加到 Prometheus 注册表 | 4 小时 | 指标基础设施 |

**风险：** 中等。接口更改触及其他文件。中断现有测试的风险很低，但需要运行完整的测试套件。

**缓解措施：** 逐步重构：添加接口，让旧的具体类型实现它，然后提取基于端点的路由。

### 阶段 3：幂等性配置化 + 内存存储（P2-P3）——第 4 周

| 项目 | 工作量 | 依赖性 |
|---|---|---|
| 将 `idempotency.enabled` 配置键添加到 `config.go` | 1 小时 | 无 |
| 添加内存幂等性存储 | 2 小时 | 配置键 |
| 在 `app.go` 中条件性实例化 | 1 小时 | 以上两者 |

**风险：** 低。`Store` 接口是稳定的，`GormStore` 经过了充分测试。

**设计决策：** 内存存储是否应该是**可选的**（当 `idempotency.enabled: true` 但无 PG 时）还是**默认的**（对于非集群部署来说更快）？建议：对于单实例部署，PG 是默认值，内存是可选的。PG 为幂等性密钥提供了崩溃安全保证。

### 阶段 4：跨实例 SSE 扇出（P1）——第 5-6 周

| 项目 | 工作量 | 依赖性 |
|---|---|---|
| 扩展发件箱中继以在所有实例上消耗 | 2 天 | 通知表设计 |
| 添加每个通知的 `instance_id` 或 `consumed` 标志以防止重复处理 | 1 天 | 表设计 |
| 更新测试以进行多实例场景 | 1 天 | 功能代码 |

**风险：** 高。这是最大的架构变更。竞争条件（一个通知由两个实例处理）需要仔细的事务语义。

**缓解措施：** 在 outbox 事件上使用 `SELECT ... FOR UPDATE SKIP LOCKED` 来确保每个事件只被一个中继实例消耗。这正是发件箱模式的用途。

### 阶段 5：搜索平衡限制 + 可观测性（P2）——第 7-8 周

| 项目 | 工作量 | 依赖性 |
|---|---|---|
| 方向 5：perKindLimit 逻辑 | 15 分钟 | 无 |
| per_kind_counts 在响应中 | 1 小时 | 无 |
| 发件箱指标（深度、最老年龄） | 1 天 | 指标注册表 |
| 限流器指标（存储桶计数、驱逐率） | 1 天 | 限流器接口 |

**风险：** 低。这些是增量更改，不影响现有行为。

### 总体风险登记册

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 限流器接口重构破坏现有测试 | 低 | 中 | 添加接口 + 用作适配器的具体类型；运行 `make test && make test-integration` |
| SSE 扇出引入重复处理 | 中 | 高 | 使用 `SELECT ... FOR UPDATE SKIP LOCKED` + 幂等交付；发件箱已经处理了至少一次语义 |
| 内存幂等性存储数据丢失 | 低 | 中 | 记录权衡：内存 = 速度，PG = 持久性。运营商选择 |
| Redis 引入的延迟 | 低 | 中 | 基于内存的限流器在单实例设置中始终可用；Redis 预留以用于多副本场景 |
| 多存储桶限流配置复杂性 | 中 | 低 | 仅公开两个存储桶系列（读/写），使用清晰合理的默认值；如有需要，运营商可以添加更多 |

---

## 总结

该代码库的整体架构是合理的。严格的分层、传输不可知的服务层、事务性发件箱和 SSO 弹性模式展示了一流的架构。五个被识别的方向是真实的差距，其严重程度各不相同：

- **P0（立即行动）：** 方向 3（XSS）和方向 4（中间件顺序）。两者都是可以在 30 分钟内修复的代码缺陷。
- **P1（第 2-3 周）：** 方向 1（端点限流）。在跨协议竞争方面有有趣的未记录边界情况。
- **P2（第 7-8 周）：** 方向 5（搜索平衡限制）。增量改进。
- **P3（第 4 周）：** 方向 2（幂等性配置）。配置哲学不一致，但运营影响较低。

然而，有一条关键路径*完全没有*被 157 个分析文档覆盖：**跨实例 SSE 交付**。对于任何非单副本部署，实时通知都会在副本之间静默丢失。这应该作为 P1 方向添加到路线图中，排在端点限流之后，在搜索平衡之前。
