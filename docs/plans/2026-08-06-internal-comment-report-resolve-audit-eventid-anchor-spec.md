# Requirements spec — internal/comment: anchor report-resolution audit EventID to the report ID

- **Direction (pinned):** anchor the report-resolution audit fact's `EventID` to the report ID so retries dedup instead of appending duplicate ledger rows. Source: `docs/auto/analyses/internal-comment-a2d7c3b3.json` direction 2 (`value 8, risk_reduction 7, effort 4, confidence 9`).
- **Companion to:** `docs/plans/2026-08-06-internal-comment-transactional-report-resolution-audit-design.md` and its change inventory. This spec is strictly narrower: it does **not** add `ResolveReportWithAudit`, does not touch the outbox/publisher path, and does not add the `check-audit-swallow` gate.
- **Tree checked:** HEAD with uncommitted prior-campaign changes; every symbol below was re-verified by grep/read, not copied from the analysis.

## 2. Requirements

### REQ-1 — The resolve-audit fact carries a deterministic EventID equal to the report ID
`internal/comment/service.go` `logResolveAudit` (:423-438) must set `AuditEvent.ID = reportID`. The report ID is a UUIDv7 generated by `idgen.NewID()` at report creation (`service.go:296`) and is unique per report; the action is the fixed constant `domain.AuditReportResolve = "comment.report.resolve"` (`internal/domain/audit.go:36`), so `event_id = reportID` is the deterministic anchor for "this report was resolved". Rationale: the dedup key is `(tenant_id, source, event_id)` (E2), and `reportID` is the only part of that key that varies per moderation action; the action and source (`"aero-id"` default via `normalizeAuditInput`, `audit_ledger.go:110-113`) are constant across retries of the same resolution.

### REQ-2 — The legacy Log adapter forwards the EventID
`internal/service/audit_ledger.go` `Log` (:136-140) must map `EventID: legacy.ID` into `AuditFactInput`. This is the single delivery path for `domain.AuditEvent` → ledger fact, used by both the parallel `internal/comment` tree (via `WithAuditLogger`) and the live twin (`internal/service/comment.go:415`), so one adapter change covers both. Without it REQ-1 is dead code (E-gap).

### REQ-3 — Retries of the same resolution are idempotent successes with exactly one ledger fact
After REQ-1+REQ-2, a second resolve of the same report (same `reportID`, same tenant context) must: (a) hit `checkAuditDuplicate` (`audit_ledger.go:157-172`) before any chain mutation and return `ErrAuditDuplicate`; or, in the concurrent case, fail the `uq_audit_ledger_tenant_event` INSERT and be mapped to `ErrAuditDuplicate` (:195-196); (b) be mapped to `nil` by `Record` (:71-73) — the caller sees success; (c) leave exactly one `audit_ledger` row, one `audit_publications` row, and an unchanged `chain_sequence` (the pre-check runs before `previous.ChainSequence + 1` at :139). No new error code, no API surface change, no schema change: `ResolveReport` behavior is otherwise unchanged.

### REQ-4 — Tenant-context precondition for dedup (documented, not changed)
The dedup key includes `tenant_id`, bound from context by `bindAuditContext` (`internal/service/audit_ledger.go:97-101`, `TenantFrom(ctx)`). Dedup therefore fires only when the retry replays the same tenant context as the original call. This spec does not add tenant plumbing to `internal/comment` (that is the companion campaign's D-A resolution); REQ-3's acceptance must construct both attempts with the same tenant context.

### REQ-5 — Scope boundary: action is not part of the dedup key
The dedup key is `(tenant_id, source, event_id)`; `action` is not a column in the constraint. `resolved` and `dismissed` share the same action constant and the same `EventID` (the report ID). Consequence, accepted by this direction: a *second, genuinely new* moderation decision on an already-resolved report (e.g., dismissed → resolved) is indistinguishable from a retry and is deduplicated to the first fact. The direction's acceptance ("simulated retry with identical anchor") pins exactly this semantic. A composite anchor or per-outcome EventID would require a schema or derivation change and is **out of scope**; do not silently "fix" this in the implementation.

### REQ-6 — No behavior change for the zero-EventID path
Other legacy `AuditLogger.Log` callers that do not set `ID` (e.g., file/block/admin paths) keep today's behavior: zero `EventID` still short-circuits dedup (`audit_ledger.go:158-160`) and `Record` still appends. REQ-2 must not coerce a zero `ID` into a non-zero value.

- Zero-EventID behavior for other legacy `Log` callers (REQ-6 keeps it).
